The TTL check fails open on bad data. `verified.iat + SESSION_TTL_SECONDS < Date.now()/1000` — if `iat` is ever missing, undefined, or non-numeric, this evaluates to `NaN < number`, which is always `false`. That means the "session expired" branch never fires and the request proceeds as if the session were fresh. A guard whose failure mode is silently permissive defeats the reason it exists (session.ts, `currentUser`). It should validate `iat` is a finite number and reject when it isn't, instead of letting malformed data slide through.

Risks: Whether this second check is deliberate defense-in-depth (a hard 1-hour session cap independent of the token's own `exp`) or accidental duplication of what `verifyToken` already enforces (per its own comment) isn't stated anywhere in the diff. Reading `crypto/verify.ts` would settle which. Separately, if `verifyToken` throws instead of returning `null` on a malformed/garbage cookie rather than a validly-signed-but-expired one, `currentUser` has no try/catch and that exception propagates uncaught.
