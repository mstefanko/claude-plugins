## UX Findings

### User & Workflow

**Who:** Developers who have installed the `bakeoff` plugin in Claude Code (separate audience from `swarmdaddy`, `obsidian-notes`, `tech-radar` even though they share the marketplace). They type natural-language requests at `/bakeoff:run`; the plugin drafts JSON work orders, asks for approval, and dispatches them to the Go `bakeoff` CLI (`research` / `build` / `validate`).

**What they're trying to accomplish in this plan:** Issue a single natural-language request and have the plugin (a) decline politely when the work isn't a good fit for Bakeoff and (b) optionally suggest splitting a large but cleanly independent request into 2–3 separate work orders before any file is written.

**Under what conditions:** Mid-flow, often in a chat where the user has already been talking about a feature/bug. They are not reading the plan doc — they only ever see the plugin's prompt strings. The plan's UX surface is therefore exactly four things: (1) the weak-fit warning string, (2) the split proposal, (3) the JSON preview + approval prompt, and (4) the resulting filenames. Everything else is internal.

---

### Observed Pain Points

- **[HIGH] The plan never anchors itself to the user.** Section headings are written for engineers ("Lightest Run Model", "Where It Belongs", "Why This Shape"). A new user opening this doc can't tell what changes in their chat. There is no "Before / After" of the user-visible behavior at the top. Add a 4–6 line "What the user will see" example before "Why This Shape".
- **[HIGH] No "what does the user type to opt out?" affordance.** The plan offers `Reply yes to continue, or tell me how to narrow it.` for the weak-fit gate and `Reply yes to continue, or tell me what to change.` for split approval, but there is no documented way to say "never warn me on this kind of request again" or "skip the fit check this once." Power users will hit this within a week. Either commit to no opt-out (and say so) or specify the flag/phrase now (`--skip-fit-check`, "always run anyway").
- **[HIGH] Two different "Continue anyway?" prompts share identical wording.** The weak-fit gate and the split approval both end with `Reply yes to continue`. In a long chat the user will see them back-to-back and may approve the wrong thing. Make the verbs differ: e.g. "Reply `yes` to draft anyway" vs. "Reply `write` to write and run these N files".
- **[MEDIUM] "Weak Bakeoff fit" is jargon a first-time user won't decode.** The phrase assumes the user has read the README's framing of Bakeoff as "two independent providers producing different useful evidence." It also pairs awkwardly with "Continue anyway?" — the sentence stem implies wrongdoing. Reframe as a recommendation, not a verdict: "Bakeoff usually pays off when …; this request looks like it doesn't need that. Run a normal agent instead, or continue with Bakeoff?"
- **[MEDIUM] The example gate messages mix audiences.** "build mode needs at least one meaningful gate verifier, such as `go test ./...`" assumes a Go user. The plugin is generic. Either parameterize per repo language or drop the language-specific example.
- **[MEDIUM] "Part" filenames are not explained to the user.** `./<base-id>-part-1.work-order.json` will land in the user's working directory with no in-chat heads-up that the file exists or how to delete/rerun a part. Add a one-line "Files written to:" preamble before approval.
- **[MEDIUM] No failure-mode coverage.** What does the user see when part 2 of 3 fails? When `bakeoff validate` rejects one of the drafted files? When the user wants to abort mid-sequence? The plan only specifies the happy path. "Risks and Open Questions" notes overwrite/rerun behavior but doesn't say what the user is told.
- **[MEDIUM] Approval is single-stage but the action is multi-stage.** One `yes` writes 1–3 files AND runs them sequentially. Users approving a write may not realize they also approved an execution sweep. Either split into two approvals (write → run) or restate explicitly: "Reply `yes` to write all three files and run them one after another."
- **[LOW] "Show all JSON blocks before writing" — JSON in chat is hostile to read.** Three back-to-back work-order JSONs will scroll users off-screen. Consider a one-line summary per part above each JSON ("Part 1 — research: how X interacts with Y") so a user can scan without parsing JSON.
- **[LOW] `--decompose=inspect` is referenced in swarmdaddy quick-start but never here.** Cross-plugin terminology inconsistency: swarmdaddy uses "decompose"; bakeoff uses "split". Users who use both will conflate them.

### Gaps (what's missing vs. what users expect)

- **No discoverability path.** A user typing `/bakeoff:run format these files` will get the warning, but there is nothing telling them where to learn more. Expected: a `--help` or `/bakeoff:help` that explains the fit philosophy in 3 lines. Plan does not specify any help surface.
- **No undo / cleanup story.** Once 3 part files are written, the user has no documented way to discard them other than `rm`. Compare to `obsidian-notes`, which is explicit about where notes land and how filenames are formed. Plan says collision policy is preserved but never tells the *user* about it.
- **No "preview only" mode.** A user might reasonably want "draft the JSON but don't write yet — let me eyeball it once more." The current flow is: show → approve once → write + run. Add `--dry-run` (or just say it's out of scope).
- **No status during sequential runs.** Sequential execution of 3 parts could take many minutes. The plan does not specify what the user sees between parts (progress, ETA, ability to cancel). Users will assume the chat froze.
- **No naming convention for the user's *original* request.** If the user wrote "add caching to the dashboard and add CSRF to the API and write a perf benchmark", what becomes `base-id`? The plan defers to "the CLI uses each work-order id" without explaining how those ids are derived from natural language. A new user has no mental model for what the resulting filenames will be.

### Content Findings

- **Labeling:**
  - "weak Bakeoff fit" / "weak-fit" / "weak-case list" / "Task-Fit Check" — four spellings/casings for the same concept across one document. Pick one user-facing label ("weak fit") and one engineering label ("task-fit check") and use them consistently.
  - "split" (verb) and "parts" (noun) are used together cleanly. But "clean-split" (hyphenated) appears alongside "split is clean" (unhyphenated). Normalize.
  - "work order" vs. "work-order" vs. "workorder" — appears all three ways across the plan and the codebase paths (`internal/workorder/workorder.go`). User-facing copy should use one form. Recommend "work order" (two words, no hyphen).
  - The marketplace.json describes bakeoff as running "two-provider research and competitive build bakeoffs." Inside the plan, the verbs are `gather`, `compare`, `analyze`, `build`. Users see four words for what marketplace.json calls two activities. Reconcile in the user-facing summary.
- **Nomenclature:**
  - Internal Go identifiers leak into user-facing reasoning: `bakeoff research WORK_ORDER`, `gather|compare|analyze`, `type`. These are fine in the plan doc but should not appear verbatim in the chat-facing strings the plugin emits. The plan should explicitly note which strings are user-visible.
  - "Bakeoff" capitalized as a proper noun in some sentences and lowercased ("bakeoff") in command-name contexts. Set a rule: capitalized in prose, lowercase in command-line/filename contexts.
  - "Beads" / `bd` / "beads-backed" appears in marketplace.json's swarmdaddy entry and in swarm-do's README but not here — good. However, a user with all four plugins installed sees beads, bakeoff, swarmdaddy, obsidian-notes, tech-radar and has no orienting "which is which" page. The plan should at least note that bakeoff is the single-request thin launcher, distinct from swarmdaddy's epic-scale orchestration.
- **Grouping / IA:**
  - Plan ordering is: Recommendation → Why This Shape → Where It Belongs → Proposed Behavior → Lightest Run Model → Implementation → Rejected → Risks → Evidence → Acceptance. This is an engineer's reading order. A user-facing reordering would put **Proposed Behavior** and **Lightest Run Model** first (the new visible behavior), then **Acceptance**, then rationale. Recommend at least adding a 1-paragraph "What changes for the user" abstract at the top.
  - "Rejected Alternatives" is good and rare — keep it. But it lives below "Implementation Work Breakdown", which buries it. Move above implementation.
- **Progressive disclosure:**
  - The default-visible content in the chat will be: warning text + 3 large JSON blocks + approval prompt. JSON is the lowest-frequency thing a user needs to *read* in full and the highest-volume thing on screen. Invert: show 3 one-line summaries by default, with JSON behind an "expand" / "show full JSON" affordance if Claude Code supports it; otherwise put summaries above each JSON block.
  - Weak-fit gate examples are excellent. The clean-split rules, by contrast, are not shown with any example dialogue. Add a worked example of a user prompt → proposed 2 parts → approval string.
- **Hierarchy:**
  - Acceptance Criteria reads as engineering DoD, not user-observable behavior. None of the criteria mention what the user *sees*. Rewrite at least one bullet in user-observable terms: "After approving a split, the chat shows the path of each file written and a one-line status per part as it runs."
  - "Suggested human-gate wording" is the most important UX artifact in this plan. It is buried inside section "1. Task-Fit Check" with a generic heading. Promote it to a top-level "User-Visible Strings" appendix so reviewers, content editors, and translators (future) can find them in one place.

### Patterns Found in Similar Products

- **`obsidian-notes` README** sets a strong precedent the plan should match: it shows *what the user types* and *what happens*, with multiple natural-language phrasings ("save this to obsidian", "record this decision"). The bakeoff plan would benefit from the same "you can say X or X' " framing for triggering the fit check, the split, and the override.
- **`swarmdaddy` README** documents an explicit quick-start flow with numbered steps and concrete slash-command examples. The bakeoff plan has no equivalent user-facing flow; it jumps to internals. Borrow that "1. install, 2. run X, 3. you should see Y" scaffolding.
- **`tech-radar` README** is explicit about prerequisites (Python, GitHub auth, fallback behavior). The bakeoff plan should similarly say "to use the split feature you do not need to install anything new" — that's actually true here (no Go changes) and is a selling point worth surfacing.

### Cross-Plugin Mental-Model Concerns

This isn't a split-the-plugin proposal — it's adding behavior inside `bakeoff`. But because the plan lives in a marketplace alongside `swarmdaddy`, users will inevitably ask "when do I use bakeoff vs. swarmdaddy?" The marketplace.json descriptions don't disambiguate well:

- `bakeoff`: "two-provider research and competitive build bakeoffs with replayable ledgers and artifact-only judging"
- `swarmdaddy`: "Beads-backed multi-agent orchestration for plans, reviews, research, and Claude+Codex routing"

Both say "research". Both involve multiple providers. A user reading these two sentences cannot pick. The plan introduces *splitting* (a tiny taste of decomposition) into bakeoff, which makes the boundary fuzzier still. Recommend the plan add a one-line "Not to be confused with swarmdaddy: bakeoff is a single-request thin launcher; swarmdaddy is multi-phase epic orchestration." The known `swarmdaddy` / `swarm-do` directory gotcha is *not* user-visible (users only type `swarmdaddy:`), so it doesn't need addressing in this plan — but the *bakeoff vs. swarmdaddy* gotcha is user-visible and does.

### Confidence Notes

- Plan is internally consistent and engineering-correct; my findings are about how it lands with a human reading the chat output, not about whether it works.
- I did not run the plugin. The warning/approval strings quoted in the plan are taken as the literal user-visible copy; if final wording differs, several pain points may not apply.
- "Will users understand which plugin to use when?" requires direct user research the plan does not have. Flagging for human validation: the bakeoff-vs-swarmdaddy boundary is a real disambiguation problem regardless of this plan, and the plan slightly worsens it.
- Sentiment around the weak-fit gate ("annoying" vs. "helpful") is explicitly flagged as a risk by the plan itself but cannot be predicted from a doc review. Needs a week of dogfooding logs.
